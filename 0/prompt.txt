## 2. Fewer LLM calls (the main lever)

- **Multi-action per step (browser-use `max_actions_per_step`)** [V]: the model outputs a list of actions. The runtime executes them in order and **stops the batch as soon as the page or DOM changes**, then re-observes. That stop rule is what makes batching safe. Your `steps` tool already does this for forms and cut submission from about 51–57 calls to 27. Extend it to navigation, e.g. "open these 5 mail rows, extract each" as one call. https://docs.browser-use.com/customize/agent/all-parameters
- **browser-use `flash_mode`** [V]: "skips evaluation, next goal and thinking and only uses memory." Output shrinks to roughly memory plus action. Their speed post measured output tokens at about 215x the per-token latency of input tokens (1k input = 29 ms; 10 output = 63 ms). They also put **history before the fresh browser state so the prefix stays KV-cacheable**, and keep action names terse (10–15 output tokens). They report about 3 s per step and 68 s per task on Online-Mind2Web for BU 1.0 [V, self-hosted benchmark]. https://browser-use.com/posts/speed-matters
- **Plan-and-Act** [P, ICML'25]: a planner writes high-level steps and an executor grounds them, with replanning after each executor phase. 57.6% on WebArena-Lite, but the gain comes from a fine-tuned planner on synthetic data. A day-sized version: one planner call per site emits a checklist (you already have code checklists), and the executor runs a batch per item. https://arxiv.org/html/2503.09572v3
- **LLMCompiler** [P, ICML'24]: the planner emits a DAG of tool calls and the executor runs independent nodes in parallel. Up to 3.7x lower latency and 6.7x lower cost vs ReAct (best-case, on QA tool tasks, not web). Applies to fan-out: "open these 18 mails / these 6 Q&amp;A pages / these N ERP materials" in parallel tabs from one decision. https://arxiv.org/abs/2312.04511
- **ReWOO** [P, 2023]: plan once with variable placeholders and execute without intermediate observations. The paper reports about 5x token efficiency on HotpotQA (from my memory of the paper; not re-checked here). Only safe for **deterministic subroutines after discovery**, such as paginating a list the model already chose.
- **CodeAct / code-as-action** [P]: the model writes Python or Playwright snippets instead of JSON tool calls, with loops and conditions in one action. The paper reports up to +20% success and fewer turns; those numbers are from my memory of the paper (not re-checked here) and are not web-specific. Risk: weak models write brittle selectors. A safer middle ground [I] is a small DSL of pre-built functions (`for_each_row(list_ref, extract=schema)`, `paginate(ref, until=...)`) that the LLM composes.
- **SkillWeaver** [P]: the agent explores a site, writes Playwright functions, tests them and reuses them. +31.8% relative on WebArena. Needs an exploration phase per site, so it conflicts with "unseen sites" unless done in-run. https://arxiv.org/pdf/2504.07079
- **Agent Workflow Memory** [P, ICML'25]: induces reusable workflows from past trajectories (offline or online). +51.1% relative on WebArena with fewer steps. Can be applied **site-agnostically**: store abstract workflows like "paginated inbox → filter → open each → extract" rather than click paths. https://arxiv.org/html/2409.07429v1
- **Agentic Plan Caching** [P, 2025]: extracts plan templates from finished runs, matches new tasks by keyword, and a small model adapts the template. -50% cost and -27% latency on average with performance maintained. https://arxiv.org/abs/2506.14852
- **WILBUR** [P]: a ranking model picks in-context demonstrations from earlier runs, plus backtracking. 53% on WebVoyager. Only relevant if you keep a demonstration bank. https://arxiv.org/abs/2404.05902

## 3. AgentOccam in detail (what they removed)

- **Removed:** `noop`; tab operations; `scroll` (full page loaded instead); most `hover` and `press`; limited `goto` and `go_forward`.
- **Changed:** choosing a dropdown option is **one click on the option ID** instead of select-then-choose.
- **Added:** `note`, `stop [answer]`, `go_home`, and `branch` / `prune` over a planning tree.
- **Biggest single jump:** action-space reduction (+11.6 points).
- **Regressions:** pivotal-node history cost 3–6 points on shopping and Reddit.
- **Main takeaway:** a smaller action vocabulary plus a full-page observation in Markdown beats elaborate machinery.
- **For us:** remove any scroll or wait-type tools, and collapse the select-then-choose sequence on cascading selects into one action.

https://arxiv.org/html/2410.13825

## 4. Frameworks: real speed tricks vs hype

- **Stagehand caching** [V]: the cache key is instruction + page content (accessibility tree) + options + URL with tracking parameters stripped. Variables are keyed by *name*, not value. A hit costs zero tokens; a miss means a fresh LLM call. The v3 docs don't describe self-healing, and the "selfHeal" retry exists only in some versions. A cache only pays off across *repeated* runs, which is only useful for us if the eval re-runs the same sites. **Observe→act**: `observe()` returns actions that `act()` replays with no LLM call. https://docs.stagehand.dev/v3/best-practices/caching
- **Skyvern code caching** [V]: records a successful run as Playwright code, replays it with no LLM, and falls back to the agent on breakage. Reported 278.95 s → 119.92 s and $0.11 → $0.04. Same caveat: it needs repeats. https://docs-new.skyvern.com/docs/features/code-caching
- **Notte perception** [V]: flattens the DOM into a labeled action space (interactive elements, form fields, section headings), with a fast heuristic mode and a deep mode. The "86% success" figure is self-reported. https://docs.steel.dev/cookbook/notte
- **AgentQL** [V]: GraphQL-shaped queries (`{ products[] { name price } }`) return JSON or Playwright locators in one call. The useful idea is **schema-shaped extraction requests**; you already have JSON extraction.
- **browser-use `extract`** [V]: a separate cheap LLM call over page Markdown returns only the answer to the main agent. Same as your background extraction.
- **Hype check:** cached replay of any kind (Stagehand, Skyvern) doesn't help on first contact with an unseen site. The real first-visit gains are terse output, prefix caching, batching, and fan-out.

## 5. Speculative and parallel exploration

- **Speculative Actions** [P, ICLR'26]: a fast model guesses the next action, it runs in parallel, and it is committed only on an exact match. Next-action accuracy was 22–38% on τ-bench retail and up to 46% top-3 on HotpotQA. **The headline 20% speedup is from chess, not web.** Only read-only or idempotent actions are safe; orders and submissions are not. https://arxiv.org/html/2510.04371v1
  - Fit for us [I]: speculatively prefetch and extract the links the model is likely to open next (mail rows, Q&amp;A items, spec revisions) in spare tabs. That is lossless and read-only.
- **Tree search (Koh et al.)** [P]: best-first search with an LM value function. +28% relative on WebArena (19.2%) at **much higher** compute. The wrong direction for us. https://arxiv.org/html/2407.01476v4
- **WebDreamer** [P]: the LLM simulates action outcomes before acting. Reported as 4–5x more efficient than tree search, but it still adds calls. Not worth it here.
- **What works:** one LLM call chooses N targets, then code opens them in parallel tabs and extracts with a schema. This is the LLMCompiler pattern applied to browsing.

## 6. One-shot structured extraction

- **Crawl4AI** [V]: HTML → Markdown, then `PruningContentFilter` (`threshold` about 0.4, about 50 ms) produces `fit_markdown`; then schema-based LLM extraction per chunk, with chunks processed in parallel. https://docs.crawl4ai.com/extraction/llm-strategies/
- **ReaderLM-v2** (1.5B, CC BY-NC) [V]: HTML → Markdown/JSON with 98% JSON pass rate. The license blocks commercial use, and it isn't needed when rule-based Markdown conversion is enough.
- **Bottom line:** extract per page (or per chunk) against a schema, not per element. You already do this. Remaining gains [I]: send Markdown, not DOM text, to extraction; deduplicate repeated rows; trim schemas (your X-4 measured -16% output).

## 1. Show all links at once and open several in parallel

**WebWalker** (arXiv 2501.07572): proven, but it is not a speedup.
- **Mechanism:** each step, the Explorer sees the page as markdown plus a list of clickable buttons with their URLs (extracted with BeautifulSoup) and picks one subpage, up to 15 steps. After each step a Critic records whether the page was useful and whether the info is now sufficient, and answers when it is.
- **Gains:** accuracy only. GPT-4o went from 33.8 (ReAct) to 37.5, at slightly more actions (4.67 vs 3.83). Strategy matters less than letting a small model see the whole link set cheaply.
- https://arxiv.org/html/2501.07572v3

**Flash-Searcher** (ICLR 2026): splits the task into a dependency graph (DAG) and runs independent subtasks concurrently. Up to 35% fewer execution steps ("up to", so best case), 67.7% on BrowseComp. https://arxiv.org/abs/2509.25301

**MindSearch:** the planner writes Python that builds a graph of sub-questions, and searcher agents work on them in parallel. Authors claim 300+ pages in about 3 minutes; this is their own claim. https://arxiv.org/html/2407.20183v2

**Infogent:** Navigator, Extractor and Aggregator agents. The Aggregator spots gaps and decides when to stop. Gains: +7% on FRAMES, +4.3% on AssistantBench. https://arxiv.org/abs/2410.19054

**WebExplorer** is training-data work, not inference speed. It is relevant only as a WebWalkerQA baseline. https://arxiv.org/abs/2509.06501

**Applying it to your agent:**
- Round 1: send the landing page's deduplicated nav and footer links (`[i] text | href | section`) plus the required schema. One call returns a ranked list of K link indices (e.g. 8–15), not one.
- Open them as concurrent Playwright pages. Run 1 extractor call per page in parallel, each filling only the schema fields it can, with source URL attached.
- Merge the results. If fields are still missing, one more call sees the union of not-yet-visited links from all opened pages and picks the next batch.
- Expect about 2–4 sequential LLM rounds instead of 10–15.
- **Speculative:** no paper benchmarks exactly "pick N links at once from a flat list". The parallel-DAG papers are the closest evidence.

## 2. Filling a form in one call

**Skyvern** has the pattern in its code. Proven: production code. File: `skyvern/core/script_generations/skyvern_page.py`.
- `extract_form_fields()` scans the page in JavaScript with no LLM call. It covers input, select, textarea and ARIA groups, and returns label, type, required flag, placeholder, options, current value and format hint.
- `dynamic_field_map()` makes **one cheap text-only LLM call**: "One LLM call sees ALL fields + ALL data and produces a complete mapping". It uses the prompt `form-field-mapper.j2` and returns `{"1": "John", "2": [...], "3": null}`. Field numbers stand in for IDs.
- Prompt rules: return the EXACT option text and never rephrase it ("I am not a protected veteran", not "No"); reformat values to the field's format hint; leave toggles null by default.
- `fill_from_mapping()` matches options without an LLM (`_match_option`), then makes an AI fallback call only when nothing matches. Native selects use `select_option(label=...)`, retried by value. React-Select style widgets get click, type the value, wait 0.5s, then click the first visible option.
- **Dependent fields:** `fill_multipage_form()` re-scans after filling. If the field count went up ("e.g., State appears after Country"), it makes a second mapping call and fills only fields that were not mapped the first time. Then it clicks Next.
- It detects a stuck page by comparing a signature built from the field labels before and after clicking Next.
- **Weakness:** the re-scan triggers only on *new fields*. A `&lt;select&gt;` that already existed but whose options reloaded is not re-mapped.

**Skyvern's custom dropdowns**, in `skyvern/webeye/actions/handler.py`:
- `sequentially_select_from_dropdown` handles nested menus up to 3 levels (30 for date pickers). It waits for animations to finish between levels.
- `IncrementalScrapePage.start_listen_dom_increment` watches the DOM so the model only sees *newly appeared* option elements.
- `classify_option_match` matches the target text to an option in tiers: exact, then word stem, then substring, then word overlap. Only if that fails does it call a secondary, cheaper LLM with `custom-select.j2`.
- Autocomplete inputs: type the text and look for a match. If none, an LLM suggests 5 candidate values to try. The loop is capped at 1 attempt "to speed up skyvern".

**browser-use** `multi_act` (`browser_use/agent/service.py`): the model returns up to `max_actions_per_step` actions (default 5). The run aborts the rest of the queue when:
- the action has the `terminates_sequence` flag (navigate, search, back, switch tab);
- the URL or focused tab changed after an action;
- an action returned an error.

It does **not** detect DOM changes on the same page, so a dependent select that reloads its options is not caught.

**Stagehand:** one `observe()` returns all field actions, then `act(field)` replays each without an LLM call. The docs claim "2-3x faster". https://docs.stagehand.dev/v3/best-practices/speed-optimization

**Recommended approach for dependent selects.** This is my design, not something a published system does.
- Before filling, find dependency candidates without an LLM: selects with no or placeholder-only options, or `disabled` fields.
- Order of work:
  1. One mapping call for all fields. It should also return the *intended label* for fields whose options have not loaded yet.
  2. Fill in DOM order.
  3. After each select change, wait for the network to go idle or for a MutationObserver to see the next select's option count change.
  4. Match the intended label to the newly loaded options with the deterministic tiered matcher.
  5. Make a fallback LLM call only when nothing matches.
- Typical cost is 1–2 LLM calls per form page.

## 3. Scripts written by the LLM

- **AutoCrawler:** the LLM writes a sequence of XPaths. If extraction fails it steps back up the DOM with "/.." (up to 5 times), then keeps the candidate that works on all 3 seed pages. GPT-4 reached 71.6% correct vs 61.9% with chain-of-thought. The authors estimate it is cheaper than calling an LLM per page once a site has more than 16 pages. https://arxiv.org/html/2404.12753v1
- **CodeAct:** code as the action format gives up to +20% success over JSON or text actions. I could not confirm the "30% fewer steps" figure. https://arxiv.org/abs/2402.01030
- **WebAgent** (Gur et al., ICLR 2024): HTML-T5 plans, Flan-U-PaLM writes the program. Over 50% better success on real websites. https://arxiv.org/abs/2307.12856
- **SkillWeaver:** the agent turns practiced tasks into reusable Playwright functions. Reported relative gains are about 31.8% on WebArena and up to 54.3% when weaker agents reuse the skills, and the paper's own figures are inconsistent. https://arxiv.org/abs/2504.07079
- **Beyond Browsing:** a hybrid of API calls plus browsing reached 38.9% on WebArena, more than 24 points above browsing alone. https://arxiv.org/abs/2410.16464

**Trade-off:** a script the LLM wrote *is* a navigation decision the LLM made, so it satisfies your rule. The risk is brittleness on sites it has not seen.
- Use it as a *batched action plan* (e.g. "fill these 12 selectors, then return `document.querySelectorAll(...)` text") with guards that hand control back to the LLM.
- Do not use it as an unchecked crawler.
- Running the LLM's JavaScript inside `page.evaluate` needs a sandbox, or at least no credentials in scope.

## 4. Prompt and cache layout

**Manus** (proven in production): https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus
- Input-to-output token ratio is about 100:1. On Sonnet, cached input costs $0.30/MTok vs $3 uncached (10x).
- Keep the start of the prompt identical across calls (no timestamps) and make history append-only.
- Serialize JSON deterministically; changing key order silently breaks the cache.
- Mask tools through token logits instead of adding or removing them.
- Drop page bodies from context but keep their URLs, so the content can be re-fetched.
- Rewrite a `todo.md` near the end of the context each step so the goal stays in view. Leave errors in the context.

**Qwen (Alibaba Model Studio):** https://www.alibabacloud.com/help/en/model-studio/context-cache
- Implicit cache: automatic, cache hits cost about 20% of the input price, no hit guarantee.
- Explicit cache: `cache_control` markers, about 10% on hits, 125% to create the entry, 5-minute TTL.
- Minimum 1,024 tokens. qwen-flash supports caching in the Beijing and Singapore regions, but is not on the US explicit-cache list.

**Applying it:** use one fixed system prompt plus the schema as the shared start for all 32 parallel extractor calls, and put the variable page content last. That way the parallel workers reuse the cached start of the prompt.

## 5. Stop as soon as the schema is filled

- WebWalker's Critic and Infogent's Aggregator are the evidence that a sufficiency check helps.
- Cheaper version: do it in Python, with no LLM. Stop when every required field is non-null and its value has been seen on the page (citation check). Each extractor returns `{field: {value, quote, url}}`.
- Spend an LLM call on the stop decision only for conflicting values.
- Skyvern's check for "0 fields mapped, so stop" is a cheap version of the same idea.

## 6. Speculation

- **Speculative Actions** (ICLR 2026): a cheap model guesses the next action and it runs in parallel, kept only if it matches the main model's choice. Up to 55% next-action accuracy, about 20% lossless latency reduction, theoretical ceiling about 50%. Only safe for actions that can be undone or have no side effects (page loads, searches). https://arxiv.org/html/2510.04371v1
- **Dynamic Speculative Planning:** learns online how many steps ahead to speculate, with a cost-latency setting. About 30% lower total cost at similar speed to the fastest lossless method. https://arxiv.org/abs/2509.01920

**Assessment:** with about 1s calls and 32 parallel calls, the cheapest speculation is *prefetching*:
- Open the top-K candidate links while the model is still deciding.
- Pre-scrape form fields after every select change.

LLM-on-LLM speculation saves little when each call is already about 1s.

## 7. Benchmarks

- **AgentOccam:** cleaning up the observation and action format alone gave +26.6 points over a plain agent on WebArena. https://arxiv.org/abs/2410.13825
- **Agent Workflow Memory:** +51.1% relative success on WebArena, with fewer steps. https://arxiv.org/abs/2409.07429
- **CUGA:** 61.7% on WebArena with a planner-executor design. https://arxiv.org/abs/2503.01861

None of these report wall-clock speed. Leaderboards rank success, not latency, so I found no strong evidence of large speedups from benchmark winners.

## Proven vs speculative

**Proven, worth doing first:**

  | Agentic Plan Caching | −50% cost, −27% latency. | https://arxiv.org/abs/2506.14852 |
