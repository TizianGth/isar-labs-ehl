## 1. Mission in einem Absatz

Wir bauen ein Agentensystem, das in einer Sandbox (20 min, bis zu 4 Chromium-Browser über CDP, nur Plattform +
4 Websites erreichbar) ein öffentliches Tender beantwortet: Vergabeportal (Ausschreibung, Bieterfragen, Konfigurator),
Lieferantenportal (Lastenheft/Spezifikation), ERP (Material, Bestand, Konditionen) und Webmail (Freigaben, TAN).
Am Ende wird **ein** signiertes Angebot im Konfigurator des Vergabeportals abgegeben. Gewertet wird:
**eligible (richtige Tender-Referenz) → Qualität 0–100 → Kosten × Zeit**. Gewinner: zuerst **privater Datensatz**
(andere Websites, anderes Layout, andere Navigation, Informationen anders verteilt!), dann public, dann Eleganz.

➡️ Wir optimieren für **Generalität und Korrektheit**, nicht für das öffentliche Szenario.

## 2. Nicht verhandelbare Regeln (Fair Play — Verstoß = Disqualifikation)

1. **Keine hardcodierten Szenario-Werte** in `agent/` — weder Code, Config, Prompts, Kommentare, Defaults, Fallbacks
   noch Tests: keine Tender-Referenzen, Materialnummern, Preise, Rabatte, Keys (`VP-…`, `TZ-…`, `K-…`, `RP-…`, `PB-…`,
   `MET-…`, `FX-…`, `ER-…`, `GR-…`), Logins, TANs, URLs-Pfade der Public-Sites. Werte aus dem **Brief** (den jeder Lauf
   bekommt) dürfen zur Laufzeit gelesen werden. Die **Regeln** (Rechenlogik) dürfen wir implementieren.
2. **Ein LLM entscheidet die Navigation**: wohin klicken, was suchen, welches Dokument relevant ist. Code darf helfen
   (Seite extrahieren, ausgewähltes Dokument parsen, vom Modell gewählte Ergebnisliste paginieren, rechnen, validieren,
   retry, Formular füllen). **Verboten**: fester Klickpfad, Crawler der alles einsammelt und am Ende einem Modell gibt.
3. Keine eigenen Browser in der Sandbox starten (nur `CDP_URLS`), keine lokalen Modelle, kein Netzwerk außer
   Plattform/Websites/Proxy, alle LLM-Calls über den Proxy (`*_BASE_URL`-Variablen).
4. Keine Secrets im Repo. Eigene API-Keys nur als Team-Secret auf der Plattform.
5. Nichts im Package, was den AI-Reviewer „steuern“ soll (Kommentare an den Reviewer zählen gegen uns).
6. `submit`/`cancel` auf der Plattform **nur nach ausdrücklicher Freigabe eines Menschen**. Test-Runs sind frei.

Details: `docs/01-challenge.md` §Fair Play.

## 4. Architektur (Kurzfassung — Details `docs/02-architecture.md`, Ist-Stand `docs/11-mvp-status.md`)

```
Brief ──► LLM-Extraktion (Referenz, Stichtag, Firma, USt-Id, Site-Rollen, autorisierte Absender je Thema)
   │
   ▼
Orchestrator (asyncio, Blackboard = append-only Extraktionen mit URL)
  ├─ Mission tender         (Browser 1)  → positions, clarifications
  ├─ Mission specification  (Browser 2)  → spec_revisions, requirements     ──┐
  ├─ Mission mail           (Browser 4)  → mail_list, mail_message           │
  └─ Missionen erp:<Gruppe> (Browser 3, je Kataloggruppe ein Tab) ◄─────────┘ (starten, sobald Spezifikation fertig)
       Explorer-Tools: click · type · select(+then_click) · fill_fields · check · set_slider · open_url · back
                       · read_all_pages(next_ref) · extract(kind) · extract_urls(urls, kind) · finish
       Fortschritts-Checkliste je Mission (vom Code aus dem Blackboard) → Auto-Finish, kein Wiederholen
   ▼
rules/resolve.py (deterministisch) → Answer + Trace → submit.py (Formular, TAN, confirm) 
```

Kernprinzipien:
- **LLM navigiert und interpretiert, Python rechnet.** Keine Arithmetik im LLM.
- **Observation = eigener DOM-Serializer** (a11y-basiert, alle Frames, Tooltips + geschlossene `<details>` sichtbar,
  `aria-hidden`/`display:none`-Köder raus, Canvas/`role=img` über `aria-label`, Zero-Width-Zeichen entfernt).
  Screenshots nur als Fallback für Vision (Qwen ist multimodal).
- **Jede Zahl hat Provenienz** (Quelle + Rohtext + Locale). Resolver wendet „neuester datierter Eintrag ≤ Stichtag,
  exakte Referenz, autorisierter Absender“ deterministisch an.
- **Immer eine Antwort abgeben.** Deadline-Wächter: spätestens bei `expires_at − 4 min` mit bestem Stand signieren.
  Leere Felder = 0 Punkte, falsche Felder = 0 Punkte → immer beste Schätzung eintragen, Positionen nie auslassen,
  außer sie lassen sich technisch nicht konfigurieren.

# Reach a sub-minute fast path without sacrificing 100/100

## Assessment

**The high-level architecture can be retained. The current execution loop needs substantial changes.** Under one minute is a plausible engineering target, but neither the existing measurements nor the research justify promising it—particularly on unfamiliar private websites.

I verified the best submission through the platform:

| Metric | Verified result |
|---|---:|
| Quality | 100/100 |
| Official duration | 200.226 seconds |
| Model calls | 203 |
| Uncached input | 470,578 tokens |
| Output | 35,622 tokens |
| Cached input, counted separately | 277,536 tokens |
| Evidence complete | Approximately 126 seconds |
| Remaining submission/signing | Approximately 75 seconds |

Your chosen budget therefore requires **about 80% fewer uncached-input-plus-output tokens**, alongside **about 70% less elapsed time**.

The main dependency chain is specification → ERP → submission. In this run, requirements became available around 49 seconds; the slowest ERP mission then needed approximately 77 seconds. Parallelizing unrelated work cannot eliminate that chain.

Retain the Decimal resolver, provenance, browser tools and model-directed investigation. Replace repeated per-page interpretation and per-position decisions with **mappings learned during the run and executed with validation**.

## Research to apply

| Research | Useful contribution | Application here |
|---|---|---|
| [LLMCompiler](https://arxiv.org/abs/2312.04511) | Dependency-aware parallel execution; reports up to 3.7× latency improvement on its benchmarks. | Dispatch work when its actual prerequisites arrive, instead of waiting for entire missions. |
| [SkillWeaver](https://arxiv.org/abs/2504.07079), [Agent Workflow Memory](https://arxiv.org/abs/2409.07429) | Reusable procedures reduce repeated interaction and interpretation. | Learn small form/table mappings within each run; reuse them across equivalent records. |
| [AXE](https://arxiv.org/abs/2602.01838), [Prune4Web](https://arxiv.org/abs/2511.21398) | Structured DOM extraction and grounded element selection. | Let Qwen identify relevant columns, fields and source nodes; let code copy their values. |
| [Observation-reduction evaluation](https://arxiv.org/abs/2605.29397) | Compression can improve speed while also reducing success. | Test preservation of decisive evidence; avoid arbitrary observation/history truncation. |
| [Budget-matched memory evaluation](https://arxiv.org/abs/2606.15017) | Extra memory/skill modules can lose their advantage once their token overhead is included. | Use compact mappings that replace calls, without adding separate reflection and workflow-induction loops. |
| [Speculative Actions](https://arxiv.org/html/2510.04371v1) | Reports 20% end-to-end lossless speedup in evaluated settings. | Overlap already-selected reads and review work; keep speculative branching out of the first implementation. |

These results support the mechanisms, **not a transferable speedup guarantee**. Do not multiply paper speedups together.

Claude is already implementing several useful pieces: submission replay, shorter extraction, TAN specialization, runtime URL reuse and vision. Extend and validate those pieces rather than building duplicate tools.

## Implementation changes

1. **Freeze the control and instrument the critical path.** Preserve the successful package with hash `f542b219…` as the benchmark control. Develop separately from the shared working copy. Record model request/response times, local slot waits, browser action times, extraction dependencies, cache usage and signing acceptance. Count failed and duplicated requests using platform totals; the current successful-response usage counter is insufficient.

2. **Make orchestration respond to facts immediately.** Start brief analysis alongside site initialization. Publish requirements individually as they are extracted and start each corresponding ERP investigation immediately. Replace model-driven `wait_for` polling of background extractions with awaiting completion events. Prepare bidder registration while evidence gathering continues, using a separate owned tab. Later amendments invalidate affected computations and checks, without restarting completed unrelated research.

3. **Learn extraction mappings instead of regenerating complete records.** Add an internal `ExtractionMap` describing the model-selected table/container, field or column mappings, locale and validation conditions. Code copies rows and values into the existing fact schemas, retaining source URL and raw text. Reuse mappings only on structurally compatible pages within the same run. Unstructured commercial prose continues through Qwen interpretation. Missing or ambiguous mappings return to the model.

4. **Reduce generated extraction output aggressively.** Store source text directly rather than asking the model to reproduce message bodies, descriptions and other verbatim passages. Return source references and semantic fields; an adapter reconstructs the existing resolver inputs. Preserve draft/preview evidence in the model’s input and validate that removing copied-body output does not repeat Claude’s observed draft-classification regression. Use separate schemas for material attributes, stock, conditions and TAN. Avoid serializing many long documents into one giant completion: fewer requests can still mean slower generation.

5. **Extend action batching and runtime form mapping.** Reuse the existing `steps` and `fill_fields` tools. Add explicit answer-field bindings to the learned submission mapping, replacing inference based only on coincidentally equal values. Execute dependent selects sequentially with fresh element resolution and readback. Stop at an unknown page, missing option, changed field identity or unexpected validation result. ERP searches and document targets remain model-selected from runtime observations; helpers execute only those selected operations.

6. **Shrink navigation context without forgetting progress.** Introduce a structured mission ledger containing selected routes, read sources, pending jobs, failed actions and remaining evidence. Supply that ledger plus recent actions and the relevant observation region. Keep full observations available on demand. Place stable instructions and schemas before changing content, but measure actual cache hits. Alibaba documents prefix caching, while its thresholds and guarantees must not be assumed for Atira’s hosted deployment. [Cache documentation](https://help.aliyun.com/en/model-studio/context-cache).

7. **Finish the browser and submission fast path.** Replace fixed settling delays with relevant URL, field, option or DOM-change conditions; Playwright already provides actionability waiting. [Playwright documentation](https://playwright.dev/python/docs/actionability). Reuse Claude’s form replay and TAN schema, and run review extraction while the requested TAN arrives. Map review tables once and compare copied values deterministically. Checkpoint the answer version, learned mappings, verified saved positions and submission stage. Following timeout or relogin, inspect server state and resume from the first unverified step; local checkpoints cannot restore unsaved server state.

8. **Handle visual content once, accurately.** Send an element crop to Qwen when canvas/image semantics do not expose the required content; associate the transcription with that page state. A canvas’s pixels are not generally available as DOM text. Clef is appropriate for choosing among observed options, rather than arbitrary transcription: its documented interface scores predefined choices without autoregressive text generation. [Cloudflare documentation](https://blog.cloudflare.com/clef-decision-models/). The existing slider guard is generic label matching, not a fixed public selector, but its broad matching should be narrowed to verified unlock gates so it cannot alter an ordinary business slider.

Public answer and fact interfaces stay compatible. New internal interfaces are `ExtractionMap`, explicitly bound form actions, a mission ledger and a resumable submission checkpoint.

## Performance targets and validation

The following are **design budgets, not measured predictions**:

| Critical-path milestone | Target |
|---|---:|
| Sites and core brief ready | By 3 seconds |
| Governing requirements available | By 15 seconds |
| Required evidence complete | By 35 seconds |
| Form complete; review/TAN underway | By 52 seconds |
| Signed acceptance | Before 60 seconds |

Target approximately **40–50 model calls**, **≤80k uncached input** and **≤8k output**, leaving margin below 100k for repairs. Measure cached-token cost separately.

Implement in this order: instrumentation and event scheduling → compact extraction/mappings → submission bindings and checkpointing → observation reduction. Keep each behavioral change independently switchable.

Validation must include:

- Existing unit, fixture and leak checks; unchanged resolver answers from replayed evidence.
- Synthetic portals with reordered columns, changed labels, mixed locales, misleading revisions, future or unauthorized approvals, and information moved between websites.
- Forms with cascading selects, equal-valued fields, changed position order, partial saves and timeout after a successful save.
- Canvas transcription, real unlock gates and unrelated sliders.
- Cancellation, failed extraction, stale mappings and uncertain final acceptance.
- Sequential alternating control/candidate sandbox runs, avoiding contention from concurrent team benchmarks.

Before claiming the fast path achieved, require **three consecutive candidate runs with 100/100, eligible, signed acceptance under 60 seconds, and ≤100k uncached-input-plus-output tokens each**. Report all attempted runs and failures. Those public results still cannot establish the same timing on the private dataset.

## Defaults and limits

- Use hosted Qwen/Clef; retain non-thinking mode for routine calls.
- Preserve 100/100: exceptional recovery may exceed both targets, as you selected.
- Keep learned site mappings scoped to the current run; package no public values or fixed public routes.
- Model-directed navigation remains mandatory under the [challenge’s fair-play rules](https://ehl-challenge.atira.ai/docs/fair-play.md).
- Test runs are permitted. Scored submission and cancellation still require explicit human authorization.
- No code was changed during this investigation.

**The decisive feasibility test is whether runtime mapping can bring evidence below roughly 35 seconds and submission below roughly 25 seconds.** If either remains above its budget, prompt caching alone will not close the gap.
